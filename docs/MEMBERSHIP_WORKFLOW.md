# Membership application workflow

## Release state

The public application page and POST endpoint remain unavailable. They reject submissions before reading a request body, so no personal details, emergency contacts, photographs, identity documents, payment references, or declarations are accepted in preview.

The repository now contains schema, validation, state-machine, private-upload, server route, and service-role-only RPC foundations for draft creation, submission, document registration, reviewer decisions, payment review, and membership activation. They are deliberately unavailable until their gates, private storage, Turnstile, durable rate limit, and live non-production evidence are complete. Do not set the membership application gate true merely because migrations are present.

## Required lifecycle

1. An authenticated applicant creates one server-issued draft.
2. The server validates and saves a numbered step for personal details, contact details, address, chapter, plan/category, photograph, identity document, emergency contact, payment method, declaration, and consent.
3. The applicant saves and resumes only their own draft or correction request.
4. The server generates the reference number and accepts submission only after all required steps validate.
5. A scoped reviewer moves a submission to under review, requires correction, approves, or rejects it.
6. The applicant may resubmit only after a correction request.
7. Membership activation occurs only under the explicit application and payment policy.

Application statuses are draft, submitted, under_review, requires_correction, resubmitted, approved, rejected, and withdrawn. The application state helper rejects applicant-controlled approval and reviewer transitions that are invalid for the current state.

## Database safeguards

- One active application per applicant is enforced across draft, submitted, review, correction, and resubmitted states.
- Reference and membership numbers are generated by the database, not accepted from the browser.
- Application steps are separate records with constrained numbers, keys, state, validation errors, and correction notes.
- Private document metadata is linked to the applicant/application and constrained to opaque random paths, approved MIME types, extensions, checksum format, and a four-megabyte server-proxied maximum size.
- RLS is enabled; browser write policies remain removed.

## Implemented server-operation contract and activation evidence

The trusted server and authenticated-RPC layer must continue to:

- derives applicant identity from the session rather than request data;
- uses the Zod schema and server-side chapter/plan lookup;
- allow-lists writable fields and ignores approval, reviewer, membership-number, payment-verification, and storage-path input;
- accepts private upload bytes only through a short-lived server-authorised intent, then validates file magic bytes, extension, MIME type, size, and owner before registration;
- creates audit and notification records without raw document or payment data;
- applies idempotency to draft/submission actions;
- brokers expiring signed read URLs only after an explicit scope check;
- emits transactional notices only after the email gate and recipient preference checks pass.

## Required validation

Run applicant, reviewer, finance, chapter-A, chapter-B, national, and administrator identities against a disposable database. Prove that an applicant cannot approve their own record, a Chapter A officer cannot access Chapter B private data, duplicate active applications are rejected, and a user cannot alter a server-managed field.
